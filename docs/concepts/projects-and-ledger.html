Projects & the ledger

#Projects

A project is a first-class container: it owns its outputs, its saved graphs, and its ledger. Everything you make lives inside the active project on disk. Switch projects from the toolbar's project selector; the whole workspace swaps.

Started building in the wrong project? File ▾ → Save project as… takes the current canvas into a brand-new project of its own — name it, pick its folder, and everything moves with it:

  • every image and clip the canvas references moves into the new project's outputs/ (same subfolders). A file that another graph in the old project also uses stays there as a copy, so nothing else breaks;
  • the ledger rows of the carried nodes move too, so 🕘 history and spend show up in the new project, and the files those past takes reference come along;
  • if the canvas was a saved graph, its file moves with it and keeps its name;
  • the graph is rewritten to the new locations and stays warm: unchanged nodes replay from cache on the next Run instead of re-paying. The graph file remembers which outputs folder it moved from (pathCompat), and every cache check tries that former location before declaring a node stale — a real edit still misses, as it should.

The old project is left with a fresh canvas. Rows that clearly belong to another graph there (they are tagged with its name) stay put. The log line under the action says how many files and rows moved and how many stayed as shared copies. Wait for a running generation to finish first — the action refuses while a job is in flight. To find any result on disk, right-click its preview → Reveal in Explorer.

  • Create a project (File ▾ → New project…) and choose where it lives — a local folder, or a share on your NAS.
  • NAS-rooted projects store their data at any absolute path (a project.json marker inside makes it portable). A second seat can Open project… on the same folder and adopt it — that's how a studio shares live work.
  • Default project keeps the legacy outputs/ location, so nothing you already made ever moves.

Projects can be exported whole (outputs + graphs + ledger) to an empty folder — the copy is itself openable — or packed into a single .brutpack file.

#The generation ledger

Every terminal generation — success, failure, or cancel — is appended to the project's ledger (ledger/generations.jsonl). Each row carries the full request context: node id, provider, model, prompt, the output paths, and the cost estimate.

Text and planning calls are ledgered too: Text → Text, Refine, the Multi-Shot planner and the cinema crew each write a planning-lane row with the provider-reported token counts, priced from the catalog's per-token rates (Marcel's own calls have their separate companion lane). No spend is invisible.

The ledger powers two things:

  • Per-node history & re-pin. Click the 🕘 on any generation node to see everything it ever produced, and pin a past result as the active output. See Never pay twice.
  • Spend. The toolbar readout aggregates the ledger into a running total, broken down by provider — and clicking it opens the full ledger: per-lane totals (generations vs Marcel's own calls) and every row newest-first with its model, status, and estimated cost.
  • Budgets. File ▾ → Project budget… sets a spend ceiling for the project. The readout shows $spent / $budget and tints as you approach it (amber past 80%, red past 100%), and every paid confirmation dialog adds an honest budget line near the cap. Budgets are soft by default — they inform, you still hold the OK. Tick hard cap and paid confirmations refuse instead until you raise or clear the budget. Comparisons use the ledger's estimates; leave the amount empty to remove the budget.

Because the ledger is written at the moment a job finalizes (not when it's submitted), jobs that were reattached after an engine restart still price and record correctly — paid work is never lost.

#Durability

Video jobs are asynchronous — you submit, then poll. Brut journals every async submission and reattaches in-flight jobs when the engine restarts, under the same job ids. If you kill the engine mid-render, the job recovers on the next launch — one ledger row, correct price. Unreadable journal entries are quarantined loudly rather than silently dropped.

#Where things live

<project>/
  outputs/        generated images & video (+ .thumbs/ display copies)
  graphs/         your saved *.brut.json graphs
  ledger/         generations.jsonl + pending/ (async job journal)
  project.json    the portability marker (for rooted/NAS projects)

Keys are never here — they live in your OS keychain.

#What a filename tells you

Every file Brut writes into outputs/ is named so the folder reads on its own, without opening anything:

<project>_<graph>_<node>_<provider>_<model>_<date>_<job>.<ext>

tournesol_facade-study_t2i-12_openai_GI25F_260923_a3f91c2e.png
tournesol_facade-study_film-3-c02_kling_K30_260923_0c77e4b1.mp4
tournesol_facade-study_sb-2-kf-s3_gemini_NB2_260923_5d10aa07.png
  • project and graph are the names you gave them, shortened to a slug (untitled while the canvas is not saved as a graph).
  • node is the node's id with its kind abbreviated (t2i Text → Image, i2i Image → Image, i2v Image → Video, ms Multi-Shot, up Upscale Image, sb Storyboard, film Film Shots, dir Director …) and, for the nodes that make several files, which one: ms-4-s07 is Multi-Shot 4's shot 7, film-3-c02 is Film Shots 3's clip 2, sb-2-kf-s3 the keyframe of card s3 on Storyboard 2 (-end for a generated end frame), dir-1-proof a proof sheet.
  • provider is who made it: the provider that actually served the call (a routed job names the aggregator, fal or openrouter), or the free local tool for its own results (conform, layers, sketch, sequence, tvai).
  • model is the model's short code, in capitals so it stands out, for model tracking at a glance. A routed job still names the model you picked; the provider segment says who served it. Free tools have no model, so the segment is simply absent.

  • date is the day it was written, yymmdd.
  • job is the first eight characters of the ledger's job id: the traceability key. It is what makes every name unique (two graphs called the same thing collide on nothing), and it is how a file finds its row: right-click any picture → Find in ledger shows the run that made it — model, node, graph, prompt, parameters, cost, date — and opens the node's 🕘 history on that row when the node is on the canvas. It works for files with the older random names too, as long as a ledger row lists them.

Files you bring in (outputs/inputs/) keep your own filename: tournesol_facade-study_facade-photo_in_260923_ab12cd34.jpg (paste for a clipboard image; the key is a content hash, so the same picture dropped twice the same day is one file). Exports keep their readable stems in outputs/exports/.

Files made before this convention keep their old names for good: a stored path is a reference, and renaming would orphan every cache and pin.

Path length. A full name is 55 to 75 characters. Windows caps a whole path at 260 characters unless long paths are enabled, so a project rooted very deep on a server has less room for the name than for the folders. Brut never fails on that: when the full path would not fit, the name drops the project and graph segments, then the node, and keeps the traceable tail (date_job), which is shorter than the old random names ever were. A shallow project root on the server stays the comfortable choice.

Your own pattern. File ▾ → Output file names… sets a per-project pattern from the tokens {project} {graph} {node} {provider} {model} {model_id} {date} {time} {job} ({model} is the short code above, {model_id} the full model id; {job} is required; the default is {project}_{graph}_{node}_{provider}_{model}_{date}_{job}). The dialog shows what a file would be called; an invalid pattern is refused with the reason. Set per seat: on a shared NAS project each machine names its own writes.
